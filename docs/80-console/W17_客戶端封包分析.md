### W17-005　`COutPacket` 建構值＝包頭序號，非 buffer 大小

- **關鍵字**：`COutPacket` `0x100` `包头序号` `功能序号` `Encode1` `Encode2` `Encode4` `EncodeStr` `EncodeBuffer`
- **來源**：短片 U38（1446790463）00:00–04:00、16:00–20:00｜`U38_短片_教學筆記.md`
- **要點**：U38 開場第一件事是**糾正上一集**——`COutPacket` 建構時收到的 int **不是**記憶體空間大小；內部永遠預設開 `0x100`（256）位元組，並把建構時傳入的那個值序列化進封包當作**包頭序號（功能序號）**。登入包用 `COutPacket(1)` → 功能序號 `1`。序列化 API 含 `Encode1`（1 byte）、`Encode2`（2 bytes）、`Encode4`（4 bytes）、`EncodeStr`（字串）、`EncodeBuffer`（原始位元組）。**客戶端 C++ 端**。
- **程式碼**：

  ```cpp
  COutPacket(long 包头序号);
  ```

  ```cpp
  char user[256] = "admin";
  char password[256] = "admin";

  COutPacket loading(1);
  loading.Encode2(0x2B);       // 寫入登入 Opcode 0x2B
  loading.EncodeStr(user);     // 寫入帳號字串
  loading.EncodeStr(password); // 寫入密碼字串
  ```

- **坑**：這是本片第一個糾錯點，也最易記錯。`EncodeString<char>(ZString<char>)` 是反組譯中所見的底層名稱，與 `EncodeStr` 對應。
- **相關**：見 W17-006

### W17-006　逐欄位還原登入協議 `0x2B`

- **關鍵字**：`0x2b` `登录协议号` `CSystemInfo` `GetMachineId` `GetGameRoomClient` `CWVSApp` `0x24` `GetPartnerCode`
- **來源**：短片 U38（1446790463）00:00–04:00、12:00–20:00、24:00–28:00｜`U38_短片_教學筆記.md`
- **要點**：依 `CLogin::SendCheckPasswordPacket` 的笔记行號逐欄位還原登入協議：功能序號 `1`、帳號字串、密碼字串、**16 位元組裝置 ID**、`GetGameRoomClient()`（直接填 0）、`CWVSApp + 0x24`（講者機器上固定為 `2`）、兩個 0、`CConfig::GetPartnerCode()`（填 0）。**銜接**：這是「發包」側的登入請求；回應 `LOGIN_STATUS` 要到 U40（借服務端）、U41（`SERVERLIST`）才還原。**客戶端 C++ 端**。
- **程式碼**：

  ```text
  14 登录协议号
     0x2b
  16 lnt: 0x2B
  17 [01 00] [05 00] [61 64 6D 69 6E] [05 00] [61 64 6D 69 6E] ....admin..admin
  18 [00 00 00 00 00 00 00 00 00 00 00 00 00 20] ........?@t...<~
  22 [01 00] : 账号字符长度
  23 [61 64 6D 69 6E] : 登录用户字符串
  24 [03 6A 64 C6 69] : 密码随机密钥
  25 [01 00 00 00] [2D 3D 13 6B 68 40 00 00 00 00 00 2D]: 机器码, hwid信息。这个可以随便乱写, 但是不透传server是起不到作用。
  28 [00 00 00 00] CSystemInfo::GetGameRoomClient() 没卵用, 可以直接写死。
  29 [00 00 00 00] 也没卵用 直接可以写死.
  30 [00 00 00 00] 共8个0. CConfig::GetPartnerCode() 合作商代码? 对应控制台的 1 ?，可以直接写死
  ```

- **坑**（衝突保留，兩邊並列）：
  - 裝置 ID 長度衝突：口述全程說 **16 位元組**；畫面筆記與程式碼是 **24 位元組**（`EncodeBuffer(pMachineId, 0x18)`）。兩層從未在片中對齊，無從判定何者為準。
  - opcode 數值三重不一致：筆記出現 `0x2B`（v000）、`0x28`（v007，`CLogin.cpp` 以 `if (id == 0x28)` 判斷）、`int16: 0x01`（v008）；口述則說「功能序號為一」。推測是不同封包層，片中未釐清。

- **坑**：⚠ 裝置 ID 長度衝突：口述 16 bytes vs 畫面／程式碼 24 bytes（`0x18`）。⚠ opcode 三重不一致：`0x2B`／`0x28`／`int16: 0x01`，且封包開頭的 `[01 00]` 筆記自身已標註歧義——**這是登入協議的關鍵位元組，錯一位整包就解析不出來**。

- **要點**：在除錯器中確認 `CLogin::SendCheckPasswordPacket` 的第二、第三個參數就是帳號與密碼（`admin`／`admin`）。IDA 的函式簽章為 `public: void __thiscall CLogin::SendCheckPasswordPacket(char const *, char const *)`；中斷後暫存器 `EAX = 0019E878`，記憶體傾印顯示 `0019E878 "admin"`（帳號）、`0019E880 "admin"`（密碼）。**銜接**：確認參數語意後，才逐欄位還原登入協議（W17-006）。**客戶端 C++ 端**。

### W17-008　`EncodeStr` 崩潰：前 4 bytes 為字串長度

- **關鍵字**：`EncodeStr` `_tagString` `m_max_buffer` `ZString` `ZXString` `崩潰`
- **來源**：短片 U38（1446790463）20:00–24:00、36:00–40:00｜`U38_短片_教學筆記.md`
- **要點**：`COutPacket::EncodeStr` 直接傳 `const char*` 或 `ZString<char>` 都會崩潰。講者除錯後發現它實際要求「**前 4 個位元組是字串長度、接著是字串本體**」的記憶體佈局，且傳入指標必須指向字串起始位址。`OutPacket.h` 確認多載簽名。可解法是手動結構體控制記憶體佈局。**客戶端 C++ 端**。**銜接**：這是 U38 內部由「能跑」走向「穩」的關鍵一步，後續 SERVERLIST 組包沿用同一套 `MaplePacketLittleEndianWriter` 觀念。
- **程式碼**：

  ```cpp
  int EncodeStr(const char* str);
  int EncodeStr(ZString<char> str);
  ```

  **版本 B-1（`start_work.cpp` / `dllmain.cpp` 畫面版本）**

  ```cpp
  struct _tagString
  {
      int m_max_buffer = 0;
      char m_str[0];      // 類似 Flexible Array Member
  };

  char name_buffer[256];
  ```

- **坑**：`_tagString` 定義在畫面中不一致——v004／v005／v010 為 `struct _tagString { int m_max_buffer; char m_str[0]; }`；v009 為多一個指標欄位 `char* m_pStr`，且賦值順序相反。口述只提「前 4 個位元組是字串長度」，未提 `m_pStr`。兩種定義不可同時正確。另 `CStringin` 寫法在 C++ 中不合法，疑為辨識／轉錄落差，**不應照抄**。

### W17-009　登入崩潰根因：全域鏈表＋作用域析構 `free`

- **關鍵字**：`CXString` `析构函数` `free` `作用域` `栈` `A90` `C6FC` `B9135` `全域变量`
- **來源**：短片 U38（1446790463）28:00–40:00、40:00–43:00｜`U38_短片_教學筆記.md`
- **要點**：把帳密字串物件從全域／函數作用域**移進小作用域**後，客戶端必定崩潰。原因是 `EncodeStr` 會把字串物件的記憶體地址**鏈進一個全域變數**（`A90`，`A90 + 0xC` 存物件地址）形成類鏈表；離開作用域時 `CXString` 析構函式把記憶體 `free` 掉（`C6FC → C6FB` 被覆寫成錯誤值，讀出 `B9135` 不可訪問地址），**伺服器回包時**客戶端再去讀已釋放地址就爆。修法：字串物件放**全域變數**或**堆（heap）**，不可用**棧（stack）**變數。**檢查點在「伺服器回包」而非「發包當下」**，初測正常、移進作用域才炸。**客戶端 C++ 端**。**收束**：U38 至此完成「發包路徑」，下一片 U39 轉入收包路徑。
- **程式碼**：

  ```text
  A90            : 全域變數；其「所有引用」都在「模板字串」序列化處
  A90 + 0xC      : 存放「模板字串物件」的記憶體地址（被 EncodeStr 鏈進來）
  C6F6 / C6F8 / C6FC : 記錄到的字串物件地址（講者當場有自我修正）
  C6FC → C6FB   : 回包處理時該欄位已被覆寫成錯誤值（少 1）
  B9135          : 從 C6FB 取出內容後得到的「不可訪問地址」
                   → 被寫回 A90 + 0xC → 下次解參考即崩潰
  ```

- **坑**：修法有條件——講者特別提醒「**如果你出了這個函數再用，它這個一樣的析構，可能還是會有問題**」，全域變數同樣有生命週期問題，並非一勞永逸。口述位址有當場自我修正且講者自承混淆（`C6F6`／`C6F8`／`C6FC`／`C6FB`、`1E55FC`），本頁保留原始混亂未強行統一。

- **要點**：本條是這條線的**登入協議中段**。先在 Java 服務端把 `getServerList(...)` 每一欄位從左到右講一遍：Opcode、serverId、serverName、flag、eventMessage、倍率欄位、頻道數量、每個頻道的四個欄位。**serverName 是寫死的**（改設定檔沒用，除非改程式再編譯；寫死為 `SCANIA`，Hex `06 00 53 43 41 4E 49 41`）；**eventMessage 才會讀設定檔**。再切 IDA＋x32dbg，`CClientSocket::ProcessPacket` 的 `case 10`（即 `0x0A`）就是世界資訊處理函式 `CLogin::OnWorldInformation`。**服務端 Java ＋客戶端 C++ 對照**。**銜接**：登入協議往 U42 的收尾推進。
- **程式碼**：

  ```java
  public static byte[] getServerList(int serverId, String serverName, int flag, String eventmsg, List<Channel> channelsLoad) {
      final MaplePacketLittleEndianWriter mplew = new MaplePacketLittleEndianWriter();
      mplew.writeShort(SendPacketOpcode.SERVERLIST.getValue());
      mplew.write(serverId);                    // 伺服器 ID
      mplew.writeMapleAsciiString(serverName);   // 伺服器名稱，例如 "SCANIA"
      mplew.write(flag);                        // 0=normal 1=event 2=new 3=hot
      mplew.writeMapleAsciiString(eventmsg);    // 登入畫面跑馬燈／公告訊息
      mplew.write(100);                         // rate modifier?
      mplew.write(0);                           // event xp?
      mplew.write(100);                         // rate modifier?
      mplew.write(0);                           // drop rate?
      mplew.write(0);

      int channelCount = channelsLoad.size();
      mplew.write(channelCount);                // 頻道數量
      for (Channel ch : channelsLoad) {
          mplew.writeMapleAsciiString(serverName + "-" + ch.getId());
          mplew.writeShort(ch.getLoad());        // Hex [64 00] = 100
          mplew.write(1);                       // server format?
          mplew.writeShort(ch.getId() - 1);      // 注意：0 基數
      }
      mplew.writeShort(0);                      // dialog
      return mplew.getPacket();
  }
  ```

- **坑**（衝突保留，兩邊並列）：
  - Opcode：口述為 `0x0A`（10＝`case 10`），但程式碼與 HeavensMS-Help 標 `0x0B`（Opcode `11`）；v002 又寫 `0x0A`（對應日誌 `[0A]`）。**未經二次確認不可直接取用**。
  - 倍率欄位標註與實際寬度不符：程式碼註解標 1 byte（`write(100)`），但講者實測客戶端是整塊用 `short` 讀取。
  - 伺服器名稱不一致：口述寫死 `SCANIA`，但 v004 Console hex 實測是 `Bazzar`（`42 61 7A 7A 61 72`）。
  - 頻道數量多說並存：口述 4 個、v000 畫面 10 個、v001 `channelCount = 2`、v004 hex 顯示 3 個。
  - 日誌格式在同一支影片出現多種（`==> 收到协议包:`／`-> [接收到数据]:`／`===> 收到客戶端封包:`／`==> 接收端封包:`），可能是不同版本 log。
- **相關**：見 W17-020、W17-021
- **坑**：⚠ **Opcode 三方衝突：口述 `0x0A` vs 程式碼／工具 `0x0B` vs v002 `0x0A`，未經二次確認不可取用。** ⚠ 伺服器名稱口述 `SCANIA` vs hex 實測 `Bazzar`；頻道數量有四種說法並存。

### W17-020　頻道 ID 為 0 基數

- **關鍵字**：`0 基數` `channelId` `writeShort(i - 1)` `C 语言数组` `頻道ID`
- **來源**：短片 U41（1465627660）03:30–07:01、14:02–17:32｜`U41_短片_教學筆記.md`
- **要點**：頻道 ID 採用 **C 語言 0 基數**：第 1 個頻道傳 0、第 2 個傳 1、第 3 個傳 2、第 4 個傳 3。Java 迴圈用 1 起算，但送進封包的 `channelId` 必須減 1。這是本集最實用的一個結論。**服務端 Java 端**。
- **程式碼**：

  ```java
  mplew.writeAsciiString(serverName);
  mplew.write(flag);
  mplew.writeAsciiString(serverMessage);
  mplew.writeShort(100);   // rate modifier
  mplew.writeShort(100);   // exp modifier
  mplew.write(0);

  int lastChannel = 1;
  ```

- **坑**：v001 版本寫 `writeShort(i + 1)`，v004／v006 寫 `writeShort(i - 1)`——**兩者只會有一個是對的**，講者本人在音軌中確認的是減 1（0 基數）。頻道容量欄位未經驗證：程式碼寫 `1200`／`load * 1200`，但口述觀察到的值是 `11`，且講者自稱「不太確定它是不是顯示的是當前頻道的容量」。「成人頻道／AdultChannel」語意不明，講者明言「我不理解是什麼意思」。

### W17-021　頻道為連續陣列，非 `p_next` 鏈結串接

- **關鍵字**：`tagChannel` `tagWorldInformation` `连续数组` `1C` `18C` `CLogin::OnWorldInformation` `p_next`
- **來源**：短片 U41（1465627660）10:31–17:32、21:03–24:34｜`U41_短片_教學筆記.md`

### W17-023　`getRecommendedWorldMessage` 固定推薦世界

- **關鍵字**：`getRecommendedWorldMessage` `RECOMMENDED_WORLD_MESSAGE` `LoginPacket.java` `GMS` `MaplePacketLittleEndianWriter`
- **來源**：短片 U42（1485212401）03:48–05:00｜`U42_短片_教學筆記.md`
- **要點**：`RECOMMENDED_WORLD_MESSAGE` 的用途是分流到人數最多（最活躍）的世界；`LoginPacket.java` 註解並指出因為我們沒有伺服器列表，所以**固定回同一個世界**——這是刻意的簡化，非 bug。講者用 Google 翻譯確認英文註解，並實作驗證。**服務端 Java 端**。**這條線就此收束**。
- **程式碼**：

  ```java
  // According to GMS, it should be the world that contains the most characters (most active)
  // however, since we do not have a server list, we should fix the world that contains the most characters (most active)

  // 推荐世界信息
  public static byte[] getRecommendedWorldMessage(int worldId, String message) {
      MaplePacketLittleEndianWriter mplew = new MaplePacketLittleEndianWriter();

      mplew.writeShort(SendPacketOpcode.RECOMMENDED_WORLD_MESSAGE.getValue());
      mplew.write(1);
      mplew.writeInt(worldId);
      mplew.writeMapleAsciiString(message);

      return mplew.getPacket();
  }
  ```

- **坑**：Java 檔案歸屬衝突——v000 確認 `getRecommendedWorldMessage` 位於作用中的 `LoginPacket.java`；v001 卻在被開啟的 `ScreenInfoRequestHandler.java` 脈絡下描述同一方法。**兩者不能同時成立**，本頁保留兩說。U42 另附 60Hz 刷新率崩潰外掛的發布與使用（非本線封包分析主軸，屬宣傳／分享性質，記錄於筆記）。
