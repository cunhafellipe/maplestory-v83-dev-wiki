### W13-003　建立帶 UI 的 Artifact `ServerApp`

- **關鍵字**：`Project Structure` `Artifacts` `JavaFX Application` `ui.ServerAPP` `ServerApp` `dist` `put into output directory`
- **來源**：S1 05:00–08:00、08:00–10:30｜`S1_2.x版本的打包方式_教學筆記.md`
- **要點**：口述權威流程為：`File` -> `Project Structure` -> `Artifacts` -> `+` 建立 **JavaFX Application** -> `from module` 選工程（口述多處辨為 `HeavenMS`）-> 輸出路徑改到 **`dist`** -> 因為是 JavaFX UI，**要把 `core` 裡面的依賴包手動加進來**（`put into output directory`）-> 取名 **`ServerAPP`**（後文亦稱 `ServerApp`）。JavaFX 分頁要指定 **Application class** ＝ **`ui.ServerAPP`**；`Title` 可設如 **`Server 083 控制台`**；長寬 **`1024` 乘以 `768`**；`Version` 可留空。最後點 `Apply` -> `OK`，再 `Build` -> `Build Artifacts...` -> `ServerApp` -> `Build`。
- **畫面層欄位（與口述衝突，參考）**：`+` -> `JAR` -> `From modules with dependencies...`；`Module` = `Heaven-ms-nap`；`Main Class` 選 `ServerApp (Gui.GUI)`；`JAR files from libraries` = `extract to the target JAR`；Output directory 為專案根目錄；`Java FX` 分頁的 `Width`／`Height` = **`750`**。
- **坑**：
  1. **Artifact 類型衝突**：口述 `JavaFX Application`，畫面四段全記為 `JAR` -> `From modules with dependencies...`。
  2. **主類衝突**：口述 `ui.ServerAPP`，畫面另有 `ServerApp (Gui.GUI)` 與 `gui.GUI` 兩種寫法。
  3. **依賴選項衝突**：口述 `put into output directory`，畫面 v000 為 `extract to the target JAR`、v002 為 `copy to the output directory and link via manifest`。
  4. **視窗尺寸衝突**：口述 `1024` × `768`，畫面 v001 為 `750`；口述另稱不設定時 ServerAPP 啟動會初始化寬高且「不可調」。
  5. **輸出目錄衝突**：口述反覆說改到 `dist`，畫面 v000 記為專案根目錄。
  6. **口述的模組名不一致**：同一支片先講「HavenMS-net」、再講「HeavenMS-client」、再講「HeavenMS 這個工程」，疑為語音辨識問題，請以本機實際 Module 名稱為準。

### W13-004　建立不帶 UI 的 Artifact `server`

- **關鍵字**：`Artifacts` `jar` `from module with dependencies` `Server` `server` `dist` `build server` `build all`
- **來源**：S1 13:00–15:30、17:30–19:19｜`S1_2.x版本的打包方式_教學筆記.md`
- **要點**：1.x 的打包方式在 2.x 仍然有效。再建一個 **jar** 型 Artifact，`for module with dependencies`，但 **`main class` 不要選 UI 方式的 `ServerApp`，要選 `Server`**，取名 **`server`** 以便區分。關鍵差異是**依賴不用手動指定**：「它默認 compile 進來的都是我們需要的。**它會把我們的依賴全部 compile 到這個 jar 包裡面去。也就是說不需要我們手動指定依賴了。**」build 時選 `build server`；只有一個 Artifact 時才適合 `build all`。
- **口述對 1.x 打包的回顧（逐字要點）**：新建 artifacts -> 打包成 jar 包 -> `from module with dependencies` -> 主類選 `server`（而不是 `serverApp`）-> 只把 output 路徑改到 `dist`，**其他什麼都不用動** -> `build` 一下 artifacts。
- **坑**：
  - **輸出到 `dist` 會互相覆蓋**。口述原話：「打包到 `dist` **可能會覆蓋**。因為它打包出來的名，就是你工程的名字。然後會把這個給覆蓋掉。」要同時保留就必須改 Artifact 的 Name 或輸出子目錄。
  - **`build all` 會把 `server` 與 `ServerApp` 兩個包都打出來**，且兩個名字幾乎一樣容易混淆。
  - 講者特別交代：**「大家打完之後不要把這個包上傳上來啊。我們我們這裡只是做一個測驗。」**
  - 畫面層另記錄 `Include in project build` 被勾選、輸出 `out\artifacts\Server_jar`，與口述的 `dist` 不一致。
- **相關**：見 W13-003、W13-005

### W13-005　兩種打包的差異核心與 Linux／Docker 適用性

- **關鍵字**：`Main Class` 選誰 `依賴處理` `core` `Linux` `Docker` `無 GUI 環境`
- **來源**：S1 一、17:30–19:19｜`S1_2.x版本的打包方式_教學筆記.md`
- **要點**：差異只有兩根，講者原話可直接引用——**Main Class 選誰**（`ui.ServerAPP` vs `Server`）與**依賴怎麼處置**（UI 版要把 `core` 的依賴包手動加進去；無 UI 版依賴會自動編進 jar）。無 UI 版的意義原話：「並且不會影響我們在 **Linux 的部署**，比如說我就是不想要我們的 GUI，但是我又想用我們 2.x 版本……那麼我們可以通過這種打包方式，然後自己打包。」並補一句「我們同樣的，我們打的這個包的話，就**不需要下面這些依賴**了。這些依賴在 **core 裡，已經被打進這個 jar 包裡面去了**。」
- **對照表（以口述為準）**：

  | 項目 | 帶 UI 版（2.x） | 不帶 UI 版（相容 1.x） |
  |---|---|---|
  | Artifact 類型 | `JavaFX Application` | `jar`，`from module with dependencies` |
  | Main Class | **`ui.ServerAPP`** | **`Server`** |
  | Artifact 名稱 | `ServerApp`（口述亦稱 `ServerAPP`） | `server` |
  | 輸出目錄 | `dist` | `dist`（**會覆蓋**，因 jar 名＝工程名） |
  | 依賴處理 | **需手動把 `core` 的依賴包加進來**（`put into output directory`） | **不用手動指定**，依賴自動 compile 進 jar |
  | 額外設定 | `Title`（例：`Server 083 控制台`）、`Width`/`Height` = `1024` × `768`、`Version` 可留空 | 無 |
  | 適用場景 | Windows／有桌面的環境 | **Linux／Docker** 等無 GUI 環境 |

- **坑**：⚠️ S8 片尾講者對 Docker 的保留說明——「其實它原來是支持 **Docker** 的……但是我覺得 **Docker 部署的場景比較少**……**Docker 它好像收費了吧**……**普通的 Docker 是沒有問題的**」，**未給出完整 Docker 部署步驟**，講者明言細節留待後續影片。S1 記的 `Docker` 也只出現在「無 UI 版相容 Linux／Docker」這句脈絡中。
- **相關**：見 W13-003、W13-004、W13-022

### W13-007　一律用 `launch.bat` 啟動，IDEA 的 JavaFX HTML 啟動器無效

- **關鍵字**：`launch.bat` `run.bat` `JavaFX HTML 啟動器` `Server-no-map.html` `build or rebuild`
- **來源**：S1 10:30–13:00｜`S1_2.x版本的打包方式_教學筆記.md`
- **要點**：build 完之後有**兩個 HTML 啟動器**（IDEA 為 JavaFX Artifact 產生的基於 HTML 啟動的方式），老師實測**無效**，原話：「**其實我試了一下，是沒有用的。不知道為什麼。反正我們也用不到**」，因為可以用 bat 啟動。實際啟動一律走 **`launch.bat`**。
- **畫面層逐字的三種啟動寫法（參考）**：

  ```bat
  @echo off
  @title HeavenMS
  set JAVA_HOME=<PROGRAMFILES>/Java\jdk1.8.0_202\bin\java.exe
  set CLASSPATH=.;dist\*
  java -Xmx2048m -D[GMS]v83=v2 -cp dist\Heaven-ms-nap.jar net.server.Server
  pause
  ```

  ```bat
  @echo off
  title mxdserver
  cd out\artifacts\Server_jar
  java -Dfile.encoding=utf-8 -jar Server.jar
  pause
  ```

  ```
  java -Dfile.encoding=utf-8 -jar Server.jar
  java -Dfile.encoding=GBK -jar <DRIVE>\code\Ms\Server-no-map\out\artifacts\Server_no_map\Server-no-map.jar
  ```

- **坑**：

### W13-017　Windows 部署：bat 包要有 `dist`、exe 包要有 `jre`，視窗都不能關

- **關鍵字**：`bat` `exe` `dist` `jre` `註冊表` `launch.bat` `Server64.exe` `視窗不能關`
- **來源**：S8 04:00–13:00、三.4｜`S8_windows和linux部署_教學筆記.md`
- **要點**：Windows 端共兩種啟動方式，**差異在於依賴什麼**：

  ```text
  方式 A：bat 腳本
    結構：<解壓後資料夾>\dist\*.jar  +  <啟動>.bat
    必須有 dist 資料夾（jar 包），因為 bat 是執行 jar 來啟動
    雙擊 bat → 黑色命令提示字元視窗；★此視窗不能關閉，關掉服務就停

  方式 B：exe 執行程序
    結構：<exe>  +  可選的 jre\ 資料夾
    沒有 dist 資料夾（jar 已打包進 exe）
    雙擊 exe → 黑色命令提示字元視窗；★同樣不能關閉
    JRE 搜尋順序：① 當前資料夾下的 jre  →  ② 註冊表中已安裝的 Java
                  （jre 資料夾可整個刪掉，仍可執行）
  ```

- **exe 的 JRE 搜尋（口述原話要點）**：「因為**編譯成 exe 以後，是依賴 jre 的**……當然你可以把它去掉。去掉以後還是能運行的。」「這個 exe 程序會**首先優先找本地的，就是，當前文件夾下面的 jre 文件夾**……如果沒有的話…**它會自動去註冊表裡面找你已經安裝好的 Java**。」
- **畫面對照的目錄結構**：路徑 `1.220(67) > jar > Server(65)`，內含 `db`、`scripts`、`wz`、`config.yaml`、`Server(65).exe`。
- **坑**：
  1. **發布包漏檔**——bat 包與 exe 包「**都沒有放 `config.yaml`**」，講者當場承認「我忘了把 config.yaml 放進去了, sorry」「**怎麼這裡也沒有 config.yaml**？完了，我這個包好像有點小問題。那我等一下要把這個包**重新上傳一下**啊。**失誤了**。」
  2. **服務視窗不能關**——bat 與 exe 啟動後的命令提示字元視窗一關，服務就停（原話「**你關閉了，程，服務就停了**」）。
  3. **exe 的 JRE 搜尋順序有環境前提**——若使用者裝了多版本 Java 或 JRE 路徑不在註冊表，exe 可能起不來；講者建議保留 `jre` 資料夾較保險。
  4. **本片沒有 Windows 服務註冊**（無 `sc create`、無服務管理員示範），只以 bat／exe 與 MySQL 起停工具的 GUI 管理。

### W13-020　Linux 部署：背景執行與日誌

  tail -f out.log                    # 監控日誌，Ctrl+C 結束監控（不中斷服務）
  ps -ef | grep java                 # 確認 Java 行程

### W13-021　Linux 部署崩潰診斷：`DatabaseConnection.getConnection` 的 NullPointerException

- **關鍵字**：`NullPointerException` `DatabaseConnection.getConnection` `MapTimer` `server.Server.main` `Channel offline`

      at java.util.TimerThread.mainLoop(Timer.java:555)
      at java.util.TimerThread.run(Timer.java:505)

  java.lang.NullPointerException
      at database.DatabaseConnection.getConnection(DatabaseConnection.java:70)
      at database.DatabaseConnection.getConnection(DatabaseConnection.java:56)
      at scripting.event.EventScriptManager.init(EventScriptManager.java:51)
      at server.Server.main(Server.java:119)
  ... (後續為 Executor 等執行緒的錯誤堆疊)
