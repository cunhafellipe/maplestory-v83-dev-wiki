### W15-001　以同一條管線理解四種傷害 Handler

- **關鍵字**：`AbstractDealDamageHandler` `parseDamage` `applyAttack` `CloseRangeDamageHandler` `RangedAttackHandler` `MagicDamageHandler` `TouchMonsterDamageHandler`
- **來源**：傷害計算介紹 00:00–05:00、45:00–50:00、48:00–52:00｜`S2_伤害计算介绍_教學筆記.md`
- **要點**：要理解任一種傷害的計算與結算，只須讀 `AbstractDealDamageHandler` 這一個父類的
  `parseDamage`（解析傷害）與 `applyAttack`（結算傷害）兩個方法。
  口述盤點出四種 Handler：`CloseRangeDamageHandler`、`RangedAttackHandler`、`MagicDamageHandler`、
  `TouchMonsterDamage…`（碰到怪物，講者自嘲不知用途、猜是類似反甲的偏門技能）。
  四者的共同點都是「先 `parseDamage` 解析、再 `applyAttack` 結算」，中間的 if 分支只是各技能的
  特殊處理；因此講者說「我講一種其實就已經代表了所有的」。
- **程式碼**：

  ```java
  // PiPiAngelServer 的 Handler 註冊
  registerHandler(RecvOpcode.USE_RETURN_SCROLL, new UseReturnScrollHandler());
  registerHandler(RecvOpcode.CLOSE_RANGE_ATTACK, new CloseRangeDamageHandler());
  ```

  ```java
  // CloseRangeDamageHandler —— 呼叫管線
  AttackInfo attack = parseDamage(slea, chr, false, false);
  ```

  ```java
  // AbstractDealDamageHandler.applyAttack 完整簽章（首次取得）
  public void applyAttack(MapleClient c, AttackInfo attack, Skill skill, int damage) {
      // ...
  }
  ```

- **坑**：`packet processor` 的正式類名無法確認——本片素材中 `Channel` 零出現，
  **不可寫 `ChannelHandler`**。`TouchMonsterDamageHandler` 的 `Handler` 後綴是筆記推補，
  音軌轉錄僅到 `touchmonsterdamage`。`MagicDamageHandler`、`TouchMonsterDamage…` 僅有口述、無畫面佐證。
- **相關**：見 W14；見 W17

### W15-002　開啟兩個除錯開關以攔截卷軸封包

- **要點**：要跟蹤伺服端收到什麼封包，先開兩個開關，再進遊戲做一次操作。

- **坑**：講者補語「上一個也可以不用，改不改成 `true` 都行，主要是改這個」——兩個開關重要性不同。
  畫面層此時段講的是 `GameConstants.GMS` 由 `false` 改 `true` 與 `SendPacketOpcode.INVENTORY_OPERATION(0x001B)`，

### W15-003　以高低 4 位拆出 `numAttacked` 與 `numDamage`

- **關鍵字**：`parseDamage` `numAttackedAndDamage` `numAttacked` `numDamage` `AttackInfo` `allDamage`
- **來源**：傷害計算介紹 05:00–10:00、20:00–25:00、25:00–30:00｜`S2_伤害计算介绍_教學筆記.md`
- **要點**：`parseDamage` 從封包讀出一個 byte 的總和，再拆成「打了幾個目標」與「打了幾段傷害」。
  口述本例 `numDamage` = 2（對應「連續攻擊兩次」）、`attackerCount`（攻擊次數）= 2、`mobCount` = 1。
  校驗通過後的各段傷害以怪物 OID 為 key 存入 `allDamage`，交給後續結算。
- **程式碼**：

  ```java
  public AttackInfo parseDamage(SeekableLittleEndianAccessor slea, MapleCharacter chr, boolean magic, boolean ... ) {
      AttackInfo ret = new AttackInfo();
      slea.readByte();
      ret.numAttackedAndDamage = slea.readByte();
      ret.numAttacked = (ret.numAttackedAndDamage >>> 4) & 0x0F;
      ret.numDamage = ret.numAttackedAndDamage & 0x0F;
      // ...後續解析邏輯
      return ret;
  }
  ```

- **坑**：口述把 `numAttacked` 說成「承受了幾次」，與程式碼語意（攻擊了幾個目標）相反；
  高低位拆分方向未經實際數值樣本驗證。講者自己也說「這個總和好像沒什麼卵用，我們先不管」。
- **相關**：見 W15-001

### W15-004　以 `itemId / 10000 % 100` 判斷武器類型

- **關鍵字**：`getWeaponType` `itemId / 10000 % 100` `MapleWeaponType` `SWORD1H` `NOT_A_WEAPON` `MapleItemInformationProvider`
- **來源**：傷害計算介紹 10:00–15:00｜`S2_伤害计算介绍_教學筆記.md`
- **要點**：要取武器類型以套用傷害係數，先用裝備 ID 除以 10000 再對 100 取餘。
  口述本例得到 `31`；畫面層 Evaluate Expression 實測 `1302064 / 10000 % 100` = `30`，
  對應 `MapleWeaponType.SWORD1H`。取不到武器時 `weapon` 會被判為 `NOT_A_WEAPON`，
  直接影響後續攻擊力計算。
- **程式碼**：

  ```java
  // MapleCharacter.calculateAttackDamageFor
  Item weaponItem = getInventory(MapleInventoryType.EQUIPPED).getItem((short) -11);
  MapleWeaponType weapon = weaponItem == null ? MapleWeaponType.NOT_A_WEAPON : MapleItemInformationProvider.getInstance().getWeaponType(weaponItem.getItemId());
  ```

- **坑**：**合法性區間口述自相矛盾**——一處說「小於 30 或大於 39 就認為他沒有穿裝備」，
  緊接著又說「我們的武器類型都是在 30 到 49 之間」，兩者互斥（見 W15-013 表第 2 列）。
  另外講者當場把自己算出的「最大基礎傷害 8」誤認為武器類型（見第 3 列）。

### W15-005　以 `ceil` 公式算出最大基礎傷害

- **關鍵字**：`calcDamageMax` `calcMaxBaseDamage` `ceil` `weaponMultiplier` `localAttack` `getTotalWATK` `1312004`
- **來源**：傷害計算介紹 10:00–15:00、15:00–20:00｜`S2_伤害计算介绍_教學筆記.md`
- **要點**：服務端先算出「你能造成的最大傷害」，超過就視為開掛。
  公式結構為 **`ceil((武器係數 × 主屬性 + 副屬性) / 100 × 武器攻擊力)`**。
  講者口算本例：物理攻擊力 `17`（`chr.getTotalWATK()` 回傳 `localAttack`）、
  武器 ID `1312004`、力量 9（主）／敏捷 4（副）、係數 `4.4` →
  `4.4 × 9 = 39.6` → `+4 = 43.6` → `/100 = 0.436` → `× 17 = 7.412` → `ceil = 8`，
  即**最大基礎傷害 = 8**。
- **程式碼**：

  ```java
  // 口述的公式（非畫面逐字，僅能確定結構）
  // ceil( (weaponMultiplier * primaryStat + secondaryStat) / 100 * weaponAtk )
  // 實測：ceil( (4.4 * 9 + 4) / 100 * 17 ) = ceil(7.412) = 8
  ```

- **坑**：**武器係數有兩套並存的常數**：口述給 0 / swing 4.4 / stab 3.2 / 弓 3.4 / 長矛矛槍 5.0；
  畫面 v003 的 `GameConstants` 給 `BOW(1.2)`、`CROSSBOW(1.35)`，且弓弩是「主 dex、副 str」
  與口述的「主力量、副敏捷」**恰好相反**（見 W15-013 表第 9 列）。
  傷害計算所在類別也三名並存（見第 11 列）。
- **相關**：見 W15-006

### W15-006　乘上技能 `effect` 得出本次攻擊最大傷害

- **關鍵字**：`effect` `combo buff` `Demon's Eye` `getCurrentMaxBaseDamage` `MapleStatEffect` `SkillFactory`
- **來源**：傷害計算介紹 15:00–20:00、40:00–45:00｜`S2_伤害计算介绍_教學筆記.md`
- **要點**：最大基礎傷害再乘技能的傷害百分比 `effect` 即為本次攻擊的傷害上限。
  本例 `effect` = `180%` → `8 × 1.8 = 14`，即**最大傷害 14**。本角色沒有 combo buff、沒有能量條、
  沒上傷害 buff，故皆跳過。其餘加成條件：特殊地圖最大傷害 **+8 萬**；吃到惡魔之眼
  （Demon's Eye）類 buff 則**最大傷害 × 1.4**；`target effect / fix` 依技能等級帶來的加成修正。
- **程式碼**：

  ```java
  // PlayerHandler.java，約 line 380：服務端取用該上限的正式 API
  // int maxdamage = player.getStat().getCurrentMaxBaseDamage();
  int maxdamage = 999999;
  ```

  ```java
  // MapleCharacter：技能等級取得
  public int getSkillLevel(int skillId) {
      return getSkillLevel(SkillFactory.getSkill(skillId));
  }
  ```

- **坑**：服務端取用上限的**正式 API 是 `player.getStat().getCurrentMaxBaseDamage()`**（畫面層證實），
  但它是否就是口述的 `calcMaxBaseDamage` 本體未證實（方法名不同）。
  「青舞飛揚」技能中文名**無法從畫面確認**（v010–v013 未拍到 WZ 介面，唯一出現的技能 ID 是 `3101004`）。
- **相關**：見 W15-005

### W15-007　將客戶端報的傷害與服務端上限對帳

- **關鍵字**：`auto ban` `maxDamage` `maxCritDamage` `allDamage` `canCrit` `element` `nature`
- **來源**：傷害計算介紹 20:00–25:00、30:00–35:00｜`S2_伤害计算介绍_教學筆記.md`
- **要點**：逐段讀出客戶端報的傷害後，先算服務端的本次攻擊上限（本例 14），再逐段比對。
  口述給的門檻有兩級：超過**服務端計算的最大傷害 × 1.5** 就開始 auto ban 記錄；
  超過 **`maxCritDamage` × 5** 則是「更深層級的封禁」。
  報的傷害類型取技能 `element`（本例 `nature` 普通，不是火／冰／閃電／毒／神聖／黑暗等需單獨計算者），
  再排除 `shadow`、`shadow meso`、`body pressure` 等分支；`canCrit` 依是否特殊職業而定，本例無。
- **坑**：**口述的 × 1.5 與畫面原始碼的 × 1 不一致**（見 W15-013 表第 1 列）；
  講者舉的「14 × 1.5」例子量級也對不上（14 × 1.5 = 21，遠小於他舉的 100）。
  `maxCritDamage × 5` 這道檢查**只有口述，畫面層未出現**。
- **相關**：見 W15-008

### W15-009　在 `applyAttack` 開頭做多道反作弊檢查

- **關鍵字**：`applyAttack` `mobCount` `attackerCount` `numAttack` `shadowPartner` `isGM` 空放 `SafeAddHP`
- **來源**：傷害計算介紹 25:00–30:00、35:00–40:00｜`S2_伤害计算介绍_教學筆記.md`
- **要點**：結算前依序檢查：取得玩家所在地圖、檢查玩家是否擁有該地圖所有權；
  **若當前職業是「新手」就不結算這個傷害**；**藍量低於技能消耗 → 封禁**；
  **玩家已死亡（非 heal 類技能）→ 跳過**；**被攻擊對象數 > 場上怪物數 → 封禁**。
  `numAttack` 之所以要判斷 `> 0`，是因為**不攻擊怪物也能放技能，這時是「空放」**，走不同分支。
  本段還會先逐條跳過大量特殊技能分支（虎咆哮、`charAttr.isCYG`、龍騎士、屬性攻擊、SafeAddHP 等）。
- **程式碼**：

  ```java
  int maxDamage = mob.getMobMaxHp();

  boolean shadowPartner = false;
  if (chr.getBuffedValue(MapleBuffStat.SHADOWPARTNER) != null) {
      shadowPartner = true;
  }

  int skillId = ret.getSkill();

  if (skillId != 0) {
      Skill skill = SkillFactory.getSkill(skillId);
      // ... 後續計算依據 skill level 與 damage limit
  }
  ```

- **坑**：**「藍量不足 → 封禁」與「玩家已死 → 跳過」只有口述，原始碼未被拍到**。
  口述點名的技能編號「`111110008`」是十一位數，與 WZ 查得的 `1121008`（七位）體系不符，幾乎確定是語音／口誤
  （見 W15-013 表第 7 列）。本段 if 分支「只點名不深入」，**這些分支的實際邏輯在本片完全缺失**。
- **相關**：見 W15-010

### W15-010　以「碼數」判定攻擊距離並記錄全屏攻擊

- **關鍵字**：距離 碼數 `distance` `ATTACK_FARAWAY_MONSTER` 全屏攻擊 魔法傷害加成

### W15-018　用 `1 − chance` 再取次方算卷軸強化門檻

- **關鍵字**：`rollSuccessChange` `testYourLucky` `scrollChangeRates` `popPercent` `Math.pow` `Math.random` `MapleItemInformationProvider`
- **來源**：卷軸概率和商城物品 15:00–17:30、17:30–20:00、20:00–22:30｜`S3_卷轴概率和商城物品_教學筆記.md`
- **要點**：機率核心算法在 **`MapleItemInformationProvider` 的 `rollSuccessChange`** 內，
  實際計算交給 **`testYourLucky`（測試你的運氣）**。
  算法是「**機率先除以 100，再用 1 減去，再取 n 次方當門檻值，最後用 `Math.random() >= 門檻` 判定成功**」。
  `n` 來自配置 **`scrollChangeRates`（默認是 `1`）**；值配得越大 → 門檻越小 → 成功率越高。
  本例 `chance = 10 / 100 = 0.1` → 門檻 `0.9`（`n` = 1）、2、3、4 時依序為 0.9 / 0.81 / 0.729 / 0.6561。
- **程式碼**：

  ```java
  // 呼叫端：rollSuccessChange 內，傳入的機率為卷軸的 success（示範值 10）
  // 演算法（依口述流程重建）
  double chance = 10 / 100;                                    // 0.1
  double threshold = Math.pow(1 - chance, scrollChangeRates);  // 預設 0.9
  boolean success = Math.random() >= threshold;                // P(>=0.9) ≈ 10%
  ```

- **坑**：`popPercent` = **`40`** 這個配置**講者沒有解釋清楚**，只說「就是卷的那個百分比，40」；
  它與 `success` 之間是否相乘**本片沒有交代，不可自行推測**。
  **`Math.random()` 是否含端點，講者自己也不確定**（原話：「包含 1，好像也包含 0 嘛，我想想，應該吧」）。
  `rollSuccessChange`、`scrollEquipWithID`、`scrollChangeRates`、`popPercent` 皆為**語音轉寫結果**，拼寫需回原始碼核對。
  上表 0.81／0.729／0.6561 與對應成功率是依口述的「0.9、0.81、0.729、0.656 依序遞減」列舉，
  **講者未逐格口頭給出**。

### W15-021　以 `CanBuy` 的三個判斷決定能否購買

- **關鍵字**：`CanBuy` `item == null` 銷售中 上架 `item.getPrice()` `return false` 176 版本 079 083
- **來源**：卷軸概率和商城物品 27:30–30:00、30:00–31:04｜`S3_卷轴概率和商城物品_教學筆記.md`
- **要點**：講者明講「**後面的我們都不看，我們重點關注的就是這個方法**」。
  購買能不能成功**只有三個判斷**：
  1. **`item == null`**——要買的東西在**服務端**找不找得到（例：176 版本的物品、或 079 有但 083 已刪的物品）→ 直接 `return false`。
  2. **是否銷售中／已上架**——「你在**客戶端**看到了，**沒用**」，還得服務端這邊有在賣。
  3. **價格比較**——`item.getPrice()` 是否**小於等於**身上所擁有的那個類型的券。
  三個都過才會往下：往倉庫添加一個商品，然後扣除你的點券。
- **程式碼**：

  ```java
  // 依口述重建（非畫面逐字）
  if (item == null) { return false; }                 // 1) 服務端找不到這個物品
  if (!item.isOnSale()) { return false; }             // 2) 沒上架／不處於銷售中
  if (item.getPrice() <= getNX(c, nxType)) { /* 加入倉庫 + 扣券 */ }
  return false;
  ```

- **坑**：上列為**依口述重建的骨架**，非畫面逐字引錄，方法簽章 `CanBuy(MapleClient, int, int)` 與
  `isOnSale()` / `getNX()` **皆為筆記重建，素材未顯示**，勿當成原始碼照抄。
  畫面層此段講的是 `CashItemOperation` 的 `operation == 14`（放到商城）與錯誤
  「道具的有效期限已结束，已废弃」，**與本條的價格判定是不同子功能**。
- **相關**：見 W15-022

### W15-022　定位購買失敗原因：價格 `2700` 大於持有皇家券 `1400`

- **關鍵字**：`2700` `1400` 皇家券 充值 改 WZ 單價 不推薦
- **來源**：卷軸概率和商城物品 27:30–30:00、30:00–31:04｜`S3_卷轴概率和商城物品_教學筆記.md`
- **要點**：本例前兩個條件都滿足，**第三個條件不滿足**：
  服務端查到的 `item.getPrice()` 是 **`2700`**，而身上只有 **`1400`**，
  所以 `return false`、買不了。客戶端上顯示的卻是「1 點券、5 點券」——
  **客戶端顯示與服務端價格落差就是購買失敗的原因**。
  講者給兩種修法：把 **WZ 裡 cash shop 的物品價格改成跟客戶端一樣（改成 1）** 能買；
  但他**明確不推薦**改 WZ 單價——「所有從服務端這裡弄過去的人，他的價格都變成了 1，那大家都可以隨便買了」，
  建議直接**往自己的帳戶充值**。
- **坑**：**改 WZ 商品單價與改 `server.properties` 開除錯開關是兩件事，勿混**。
  實務上要測試應改自己的帳戶餘額，而不是改共用 WZ。
- **相關**：見 W15-020、W15-021

### W15-023　改點券前先停服務端，改的是 `accounts` 三個券欄位

- **關鍵字**：`accounts` `characters` `nxCredit` `NX Credit` `Maple Point` `nxPrepaid` `NX Prepaid` 停服務端 存檔覆蓋 `99999` `select * from accounts`
- **來源**：修改点券 00:00–03:30、03:30–07:00、07:00–10:30、10:30–12:00｜`S5_修改点券_教學筆記.md`
- **要點**：點券存在 `accounts`（**帳號表**）的三個欄位：**`NX Credit` / `Maple Point` / `NX Prepaid`**，
  實作上 `nxCredit` 與 `nxPrepaid` 都要改，講者說「**把這三個都改一下**」。
  **全片最重要的操作原則：改資料庫前一定要先把服務端停掉**——
  服務端啟動時資料已載入記憶體，改資料庫不生效；而關服時伺服器會把記憶體存檔回寫，
  **把你的修改覆蓋回去**（講者示範：改成 `99999`，結果被覆蓋回 `0`）。
  刪角色則是改另一張表 **`characters`（角色表）**，不是 `accounts`；
  遊戲前端擋下的「PSC 碼」其實是**伺服器端的安全交易碼驗證**，該機制未提供就無從輸入。
- **指令**：

  ```sql
  -- 查詢帳號表
  SELECT * FROM accounts;
  ```

  ```sql
  -- 教學語境中的「刪除行」對應寫法（口述原文：「或者 alter 加 delete」）
  DELETE FROM characters WHERE id = 1;
  ```

- **坑**：**三種券的對應關係講者自己也不確定**——原文「第一個是皇家點券吧，第二個是點券，
  第三個應該是抵用券。應該是，我也，我也不太清楚，應該反正就是這三個，你自己改一下看看」。
  口述把「刪除行」講成「**alter 加 delete**」（`ALTER` 改結構、`DELETE` 刪資料列，兩者不同層級）。
  畫面層實際是用 Navicat／DBeaver 網格介面的「刪除行」按鈕，**沒有**貼 `DELETE` 進 SQL 編輯器。
  點券數值口述與畫面不同（`99999` vs 畫面 `123456`；口述結尾又報 `999999`），本筆記兩者並列，不代為選定。
  示範中的 `root` 連線與 `admin`/`admin` 弱密碼僅適用於本機單機測試環境。
- **相關**：見 W15-024
